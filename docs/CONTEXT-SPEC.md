# The `.context` File Format

**Version 0.1** · status: draft · license: CC-BY-4.0 (spec), MIT (reference impl)

`.context` is a plain-markdown, self-describing context file for AI coding
agents. It is what you get when you stop dumping your repository into a
prompt and start *rationing* it.

## Design goals

1. **Agents already speak markdown.** No new parser, no new protocol.
2. **Self-describing.** Stats, scoring, and provenance travel inside the
   file, so the agent (and the human) can audit what was cut.
3. **The map is the contract.** Every file in the repo appears in the map
   with a relevance score — even files whose bodies were cut for budget.
   The agent can request any of them by path. Cutting content is fine;
   hiding the file system is not.
4. **Cheap to diff.** Two consecutive `.context` files should be easy to
   compare — that is what `vp diff` produces.

## Structure

```markdown
# context · <repo-name> · <git-branch>

> generated by <generator> <version> · profile: <profile> [· task: "..."] [· scope: changed files only]
> <ISO-8601 UTC timestamp>
> <one line telling the agent how to use the file>

## stats
| metric | value |
| --- | --- |
| files | <included> of <total> (<pct>%) |
| tokens (est) | <included> — raw <raw> (<reduction>%) |
| cost / prompt | <now> — was <raw> · <model> @ $<price>/MTok |
| repo | <name> · <primary language> · <branch> |

## task focus            (optional — present when a task was given)
terms: <comma-separated terms>. best-matching included files:
- `<path>` · <matched>/<total> terms

## changed               (optional — git-aware mode)
- <status char> `<path>`

## map
- `<path>` · <kind> · <tokens> tok [· score <n>] [· NOT included (<reason>)]

## files
### `<path>` — <tokens> tok · score <n>
```<language-fence>
<pruned file body>
```
```

## Sections

### `stats` (required)
Audit header. Token counts are estimates and should be labeled as such.
`raw` = the naive-paste baseline (every text file, full content, including
lockfiles — what a `cat **/*` would send). This number is the entire
argument for the format's existence, so it must be honest.

### `task focus` (optional)
When the generating tool was given a task, it lists the terms used for
matching and the top matched files. This lets the agent verify the ranking
wasn't magic.

### `changed` (optional)
Git-aware mode: the working-tree status of every changed file, so the agent
knows what is fresh work.

### `map` (required)
The complete file inventory with kind, raw token estimate, relevance score,
and inclusion state. This section is what makes `.context` trustworthy:
nothing is hidden, everything is priced.

### `files` (required, possibly small)
Full (pruned) bodies of the selected files, ordered by score, descending.
Pruning is allowed to: strip trailing whitespace, collapse blank-line runs,
strip full-line comments (when the profile says so), and truncate long
files with a visible `... [truncated]` marker. Pruning must never change
program meaning.

## Scoring (informational)

vibe-pilot v0.1 scores files as:

```
score = 3.0·task_relevance + 2.0·git_recency + 1.5·import_centrality
      + 1.0·path_proximity + bonuses − kind_penalties
```

The formula is deliberately public and boring. Other generators may use any
scoring they like — the map format does not change.

## Kinds

`source · test · config · doc · rules · lockfile · generated · asset ·
binary · secret · data · other`

Two kinds are normative:

- **`lockfile` / `generated`** — counted in `raw`, never emitted in
  `files`. They are the noise floor.
- **`secret`** — the file's content must never be read, by any conforming
  generator. `.env`, `*.pem`, keys, credentials.

## Consumer behavior (recommended)

An agent given a `.context` should:

1. Read `stats` to calibrate expectations.
2. Treat `map` as the ground truth of the file system.
3. Ask for map-listed files by path when it needs bodies that were cut.
